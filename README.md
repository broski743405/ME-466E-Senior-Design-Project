# UTME Weeble -- controls + MuJoCo simulator

One code base for the ESP32 firmware and the simulator. The flight logic in `include/weeble_core.h`
runs unchanged in both places. Every physical number lives in **one file**, `drone_config.py`.

```
drone_config.py        <- EDIT THIS when the hardware changes (mass, CG, inertia, geometry, motors, IMU...)
build.py               <- turns the config into the MuJoCo model + C++ header, compiles the simulator library
weeble_sim.py          <- run one flight (window, headless, or record a video)
run_tests.py           <- fly every routine under 7 "real drone differs from the model" conditions
platformio.ini         <- ESP32 build (unchanged)
include/
  weeble_core.h        <- flight logic (estimator, attitude, descent, hop, ascent, supervisor, mixer)
  weeble_config.h      <- GENERATED by build.py (do not edit)
  weeble_muscles.h     <- ESC + servo drivers (your file, unchanged)
src/main.cpp           <- ESP32 firmware (serial commands, IMU setup, 200 Hz loop)
sim/
  weeble_bridge.cpp    <- C functions so Python can call weeble_core.h
  WeebleDrone.xml      <- GENERATED MuJoCo model
  model_info.json      <- GENERATED numbers for weeble_sim.py
```

This replaces the old `weeble_sim.py`, `WeebleDrone.xml`, `weeble_bridge.cpp` and `weeble.dll` in the project
root. The old `sim_test.cpp` (planar test) used the old API and is superseded by `run_tests.py`.

## 1. Quick start (Windows)

1. Python 3.10+ with `pip install mujoco numpy imageio imageio-ffmpeg`.
2. A 64-bit C++ compiler on the PATH as `g++` (MinGW-w64 / MSYS2). Check: `g++ --version`.
3. In this folder:

```
py build.py                          # model + header + sim/weeble.dll, prints a summary
py weeble_sim.py hop --cg-dz -20     # watch a 5 ft hop (window). See section 4 for why --cg-dz -20
py weeble_sim.py ascent --height 0.8 --cg-dz -20
py weeble_sim.py descent --cg-dz -20
py weeble_sim.py hop --cg-dz -20 --no-viewer    # no window: log + result report
py weeble_sim.py hop --cg-dz -20 --record 8     # saves weeble_hop.mp4
py run_tests.py                      # the full robustness table (about 15 s)
```

The report at the end of every run is **ground truth from MuJoCo** (where it really landed, how fast),
not what the controller believes.

## 2. When the hardware changes

1. Open `drone_config.py`, change the numbers. Mass properties are copied **as Onshape shows them**
   (grams, mm, g mm^2, relative to the CAD origin), plus the origin's height above the base bottom.
2. `py build.py`. Read the summary: total mass, CG height, **self-righting margin**, thrust-to-weight,
   gimbal kick-back limit, and warnings.
3. `py run_tests.py` to see whether the routines still pass.
4. For the ESP32: rebuild/upload in PlatformIO. `include/weeble_config.h` already has the new numbers.

The simulator refuses to run if `drone_config.py` changed since the last `build.py` (the compiled library
carries a fingerprint of the config), so you cannot accidentally fly an old model.

Things you will most likely update: `CAD_*` (mass/CG/inertia), `EXTRA_MASSES` (props, payload: set
`enabled=True`), `IMU_POSITION` / `IMU_AXES`, `THRUST_MAX_N`, `MOTOR_LAG_*`, `POD_*`.

## 3. What each routine does

**Descent (20 ft drop).** Hangs from the mothership, detects free fall (< 0.35 g for 40 ms), takes a 0.1 s
"true zero-g" accelerometer reading, then brakes along a curve that says "the fastest I may be falling at
this height". The curve accounts for the motors still spinning up: while thrust builds, the drone keeps
accelerating at (g - thrust/mass), which the old curve ignored (it landed at 2.5-4 m/s; this one at ~0.7).
It plans with 45 % of the spare deceleration, so a weaker battery is absorbed.

**Hop (5 ft).** No longer ballistic: a ballistic hop arrives with ~2.4 m/s sideways speed and the round base
rolls 1-2 m past the target. Now it is a short powered flight:
settle -> spin up and level -> climb to 0.2 m -> fly to the target -> hover -> sink slowly -> cut motors on touchdown.
The path is "minimum jerk": position, speed and acceleration all start and end at zero, so the drone
arrives over the target almost stopped and lands with < 0.3 m/s sideways.

**Ascent.** Same machinery with zero distance: climb to the height, hover `ASCENT_HOVER_S`, land softly.

## 4. Big findings about the hardware (read this)

1. **The CAD CG is not self-righting.** The CG is 100.7 mm above the base bottom and the base's R100 sphere
   centre is 100.0 mm above it, so the CG sits **0.7 mm above** the centre of curvature. A weeble needs it
   *below*. In the sim the drone rolls over to ~28 deg as soon as it is set down. All tests therefore use a
   stand-in "design fix": CG 20 mm lower (`--cg-dz -20`). Moving the battery/payload low does this.
   Even then it only self-rights within ~27 deg: beyond that the side band's curvature centre is below the CG.
2. **Thrust.** The vendor listing for the CRM2413A gives ~16.6 N (1696 g at 12.6 V with two 9050 props),
   not the 27.25 N in the old code. With 1024 g that is T/W 1.65. **Adding the 454 g payload would drop it to
   ~1.15**, which is too little for hop/ascent margins. Measure thrust on a scale at real battery voltage.
3. **Motor lag** (time to 63 % thrust) is a placeholder (0.10 s). Measure it with `spin` (section 7).
4. **Gimbal kick-back.** The motor stack is heavy (~190 g) and its CG may sit above the fisheye. Swinging
   it fast kicks the body the other way; above ~7 Hz that kick beats the thrust torque. The attitude loop
   keeps itself well below that automatically, but it depends on `POD_MASS_G` / `POD_COM_ABOVE_PIVOT_MM`,
   which are guesses. Weigh the stack and find its CG.
5. **IMU-only navigation limit.** Position comes from integrating the accelerometer. A 0.1 deg tilt error or
   0.05 m/s^2 accelerometer drift costs ~0.3-0.6 m over a 5 s flight. That is why the hop is kept short.
   The sim hop lands within 50 cm almost always, but **few-centimetre accuracy needs a ground-relative
   sensor** (e.g. an optical-flow sensor + downward time-of-flight rangefinder).

## 5. How the controller works (plain words, then the math)

**Estimator** (`Estimator`): the gyro is integrated to track orientation; while the drone is still on the
ground the accelerometer gently corrects it toward "up" (Mahony filter, only when not rotating and not
accelerating). Orientation turns body accelerations into world accelerations, which are integrated twice
for velocity and position (dead reckoning). While sitting on the ground before liftoff, position and
velocity are held at zero. If the IMU is not at the CG, the extra "spinning" accelerations are removed:
`f_cg = f_imu - w x (w x r) - alpha x r` with `r` from the config.

**Attitude** (`AttitudeCtl`): we want the body lean to behave like a spring + damper:
`alpha = wn^2 * err - 2*zeta*wn * rate + ki * integral(err)`. Torque needed = inertia * alpha. The gimbal
makes torque = thrust * arm * sin(tilt), so `tilt = asin(I*alpha / (T*arm))`. Inertia and arm come from the
config and T from the motor model, so the response stays the same when hardware changes. Two limits:
- `wn` is capped at 15 % of the kick-back frequency `sqrt(T*arm / I_couple)` (lower at low thrust).
- On the ground, thrust through the base's centre of curvature tips the drone with moment
  `(T*R - m*g*margin)*sin(lean)`. That is cancelled directly (the gimbal acts with arm = pivot height above
  the contact point). Without this, spin-up on the ground is unstable.

**Height and position** (`PoweredFlight::flyTo`): the reference path gives position, speed and
acceleration; the command is `a = a_path + kp*(p_ref - p) + kd*(v_ref - v)` (plus a small integral for height).
Horizontal acceleration becomes lean: `lean = atan(a_horizontal / (g + a_z))`. Thrust =
`m*(g + a_z) / cos(tilt) / k`, where `k` = learned real/modelled thrust.

**Thrust learning**: in free flight the accelerometer reads exactly thrust / mass, so comparing it with the
motor model tells us if the battery has sagged or `THRUST_MAX_N` is wrong. It only learns while thrust is
steady (otherwise a motor-lag mismatch would look like weak motors). At takeoff, if the motors reach hover
thrust but the drone is still on the ground, a boost ramps up until liftoff; liftoff is read straight
from the accelerometer (> 1 g means thrust beat weight).

**Touchdown** (hop/ascent): an impact spike, or the ground carrying part of the weight (specific force
above what thrust alone gives), or sinking much slower than commanded *while* the ground carries some
weight. After the motors cut, the gimbal keeps holding the body level while the props spin down
(any thrust on the ground tips a round base).

All gains are in `Params` at the top of `weeble_core.h`, each with a comment.

## 6. Test results (current config, CG -20 mm stand-in)

`py run_tests.py`: **20 / 21 pass**. Descent touchdown 0.70-0.83 m/s in every condition; hop rests 5-27 cm
from the target; ascent apex 0.62-0.67 m for a 0.60 m target. The one failure: ascent when the real motors
are 2.5x slower than the controller believes (apex 0.96 m) -- measure the lag and enter it. Across 8
random noise seeds the hop lands 1-31 cm out nominally; with a much worse IMU, 2 of 8 seeds exceeded 50 cm.

Not simulated: the 4-bar linkage (the sim drives the pod angle directly; `mix()` still converts for the
real servos), aerodynamic drag/ground effect, real ESC/RPM-loop behaviour (modelled as a first-order lag),
TPU compliance. The side band of the shell comes from `SHELL_PROFILE_MM` read off the CAD picture;
set `SHELL_STL` to your exported shell STL (CAD coordinates, mm) for the exact shape.

## 7. Firmware (src/main.cpp)

Fixes vs the old main.cpp: the MPU6050 ranges and low-pass filter are now actually written (the old code
left the chip at +-2 g / +-250 dps while reading it as +-8 g / +-1000 dps: accel 4x too high, gyro 4x too
low), the axis mapping comes from the config, `cal` exists and refuses if the drone is moving, ascent/servo/
spin/pose commands added, ESC KV/battery/max RPM/pulse rate from the config.

Bench procedure:
1. `unlock`, `servo 10 0`, `servo -10 0`, `servo 0 10`, `servo 0 -10`, `servo` (off). Check the motor stack
   tilts the right way and does not bind: +x tilt should push the top of the drone toward body +x.
2. `cal` with the drone still. Then `status`: tilt should match reality.
3. Thrust + lag: drone on a scale (or tethered), props on: `arm`, `cap 100`, `spin 50 3`. The stream prints
   time, RPMs and accel. Thrust at each % on the scale gives `THRUST_MAX_N`; the time for the RPM to cover
   63 % of its change after the start gives `MOTOR_LAG_UP_S`, and after the stop gives `MOTOR_LAG_DOWN_S`
   (thrust goes with RPM squared, so thrust lag is roughly half the RPM lag -- the scale reading is better).
4. Only then flights, starting with a low `ascent 0.3`.
